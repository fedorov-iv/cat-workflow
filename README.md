# cat-workflow — прототип конструктора бизнес-процесса заявок

Песочница для обсуждения: матрица переходов по статусам в привязке к проекту и конструктор форм АРМ,
которые собирают данные при смене статуса. Модели `core` — упрощённые копии `rall`
(`Project`, `TicketApplication`, `Transfert`, ...).

## Запуск

```bash
python3.12 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python manage.py migrate
.venv/bin/python manage.py seed_demo          # admin / admin, 3 проекта, 9 заявок
.venv/bin/python manage.py runserver
```

- http://127.0.0.1:8000/arm/ — АРМ: заявки и кнопки переходов. Формы открываются в Bootstrap-модалке
  (AJAX: GET отдаёт фрагмент `arm/_transition_modal.html`, POST — JSON `{ok, redirect}` или `{ok: false, html | error}`);
  без JS та же форма открывается отдельной страницей
- http://127.0.0.1:8000/admin/workflow/ — конструктор
- http://127.0.0.1:8000/api/docs — интерактивная документация API (Swagger UI)
- `GET /api/applications/<id>/transitions/` — доступные переходы и JSON-схемы их форм
- `POST /api/applications/<id>/status/` — `status=<базовый статус>` + параметры (как сейчас в API платформ)
  или `transition=<код>`; заголовок `X-Api-Key: demo-key`

Тесты: `.venv/bin/python manage.py test core`

## Как устроено

| Слой | Где | Что |
|---|---|---|
| Конфигурация (БД) | `workflow/models.py` | `Workflow` проекта, `WorkflowStatus` (проектный статус → базовый), `WorkflowTransition` (кнопка, каналы, форма), условия и действия перехода, `TransitionForm` + поля, справочники `ChoiceSet`, журнал `TransitionLog` |
| Контракт интеграций | `workflow/base_matrix.py` | Базовые статусы и допустимые переходы между ними. В `status` заявки всегда лежит базовый статус |
| Блоки (код) | `workflow/registry.py`, `workflow/builtin.py`, `core/workflow_hooks.py` | Реестры привязок полей (bindings), условий (guards) и действий (effects). Админка выбирает блок и задаёт параметры, но не пишет логику |
| Движок | `workflow/engine.py` | `available_transitions`, `get_form`, `execute`, `execute_by_code`, `transition_to_base` |
| Проверка конфигурации | `workflow/validation.py` | Базовая матрица, неизвестные блоки и параметры, недостижимые статусы и тупики, обязательные поля для базовых статусов, неоднозначность для API |
| Перенос | `workflow/serialization.py` | Экспорт/импорт JSON, клонирование в другой проект |

`execute` в одной транзакции: блокировка заявки → проверка статуса и канала → условия →
валидация формы → запись в поля моделей через привязки → смена статуса → действия → журнал.
Сигнал `transition_executed` (заглушка Kafka) — после коммита.

Данные форм пишутся только в существующие поля моделей. В журнал попадают имена заполненных привязок,
значения — нет.

Поля-списки в конструкторе формы:

- **Вид списка** — простой или с автокомплитом (Tom Select, поиск по уже загруженным вариантам).
- **Зависит от списка** — другое поле этой же формы. Связь значений:
  - справочник: у значения задаётся «При значениях родителя» (через запятую, пусто — доступно всегда);
  - список из модели: по внешнему ключу между моделями вариантов (поток → курс), находится автоматически.

  Сервер проверяет, что выбранное значение подходит к родителю; в JSON-схеме формы есть `widget`,
  `depends_on` и `parents` у вариантов. Ошибки настройки (родитель не список, нет связи моделей, цикл)
  показываются при сохранении формы и процесса.

## Демо-данные

- **Код будущего** — 7 статусов, из них «Проверка документов» — собственный статус проекта с базовым
  `approved`. Условия: статус трансферта, закрытый поток, флаг в settings. Отчисление с документом,
  который обязателен только при уважительной причине, и уточнением причины — список с автокомплитом,
  зависящий от выбранной причины. Поток при одобрении выбирается из списка с автокомплитом.
- **БАС** — короткий процесс без одобрения; отчисления запрещены настройкой проекта, кнопка видна как заблокированная.
- **Цифровые профессии** — без процесса: такие заявки остаются на старом коде.

## Перенос в cat-marketplace

- `workflow/` переносится как есть (под Django 2.0: `models.JSONField` → `jsonfield.JSONField`,
  `path` → `url`, убрать `@admin.display/@admin.action`).
- `core/workflow_hooks.py` → `rall/workflow_hooks.py`: привязки к `TicketApplication`/`Transfert`,
  условия и действия из `TicketApplication.change_status` и `Enrollment`.
- Переключение старого и нового кода — по наличию активного `Workflow` у проекта, в `Enrollment.change_application_status`,
  `finish_course`, `change_enrollment_status` и местах прямого вызова `change_status`.

Сознательно не сделано: сидинг процессов текущих проектов (PDC, BAS, KB), цепочка модулей КБ,
смена курса и «Уточнить информацию» как переходы-петли, права по ролям на уровне перехода.
