# cat-workflow — прототип конструктора бизнес-процесса заявок

Песочница для обсуждения: матрица переходов по статусам в привязке к проекту и конструктор форм АРМ,
которые собирают данные при смене статуса. Модели `core` — упрощённые копии `rall`
(`Project`, `TicketApplication`, `Transfert`, ...).

## Запуск

```bash
python3.12 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python manage.py migrate
.venv/bin/python manage.py seed_demo          # admin / admin, 3 проекта, 9 заявок
.venv/bin/python manage.py runserver
```

- http://127.0.0.1:8000/arm/ — АРМ: заявки и кнопки переходов. Формы открываются в Bootstrap-модалке
  (AJAX: GET отдаёт фрагмент `arm/_transition_modal.html`, POST — JSON `{ok, redirect}` или `{ok: false, html | error}`);
  без JS та же форма открывается отдельной страницей
- http://127.0.0.1:8000/admin/workflow/ — конструктор
- http://127.0.0.1:8000/api/docs — интерактивная документация API (Swagger UI)
- `GET /api/applications/<id>/transitions/` — доступные переходы и JSON-схемы их форм
- `POST /api/applications/<id>/status/` — `status=<базовый статус>` + параметры (как сейчас в API платформ)
  или `transition=<код>`; заголовок `X-Api-Key: demo-key`

Тесты: `.venv/bin/python manage.py test core`

## Как устроено

| Слой | Где | Что |
|---|---|---|
| Конфигурация (БД) | `workflow/models.py` | `Workflow` проекта, `WorkflowStatus` (проектный статус → базовый), `WorkflowTransition` (кнопка, каналы, форма), условия и действия перехода, `TransitionForm` + поля, справочники `ChoiceSet`, журнал `TransitionLog` |
| Контракт интеграций | `workflow/base_matrix.py` | Базовые статусы и допустимые переходы между ними. В `status` заявки всегда лежит базовый статус |
| Блоки (код) | `workflow/registry.py`, `workflow/builtin.py`, `core/workflow_hooks.py` | Реестры привязок полей (bindings), условий (guards) и действий (effects). Админка выбирает блок и задаёт параметры, но не пишет логику |
| Движок | `workflow/engine.py` | `available_transitions`, `get_form`, `execute`, `execute_by_code`, `transition_to_base` |
| Проверка конфигурации | `workflow/validation.py` | Базовая матрица, неизвестные блоки и параметры, недостижимые статусы и тупики, обязательные поля для базовых статусов, неоднозначность для API |
| Перенос | `workflow/serialization.py` | Экспорт/импорт JSON, клонирование в другой проект |

`execute` в одной транзакции: блокировка заявки → проверка статуса и канала → условия →
валидация формы → запись в поля моделей через привязки → смена статуса → действия → журнал.
Сигнал `transition_executed` (заглушка Kafka) — после коммита.

Данные форм пишутся только в существующие поля моделей. В журнал попадают имена заполненных привязок,
значения — нет.

Поля-списки в конструкторе формы:

- **Вид списка** — простой или с автокомплитом (Tom Select, поиск по уже загруженным вариантам).
- **Зависит от списка** — другое поле этой же формы. Связь значений:
  - справочник: у значения задаётся «При значениях родителя» (через запятую, пусто — доступно всегда);
  - список из модели: по внешнему ключу между моделями вариантов (поток → курс), находится автоматически.

  Сервер проверяет, что выбранное значение подходит к родителю; в JSON-схеме формы есть `widget`,
  `depends_on` и `parents` у вариантов. Ошибки настройки (родитель не список, нет связи моделей, цикл)
  показываются при сохранении формы и процесса.

## Настройка из админки

Вход: http://127.0.0.1:8000/admin/ (после `seed_demo` — `admin` / `admin`). Всё, что описано ниже, лежит в разделе **Конструктор бизнес-процессов**. У проекта может быть только один бизнес-процесс. Пока он выключен или его нет, заявки проекта идут старым кодом: в АРМ у такой заявки написано «Процесс не настроен».

Настраивать удобно в таком порядке. Форма и справочник общие для всех проектов, процесс принадлежит одному проекту.

1. Справочник, если сотруднику нужно выбрать значение из списка (причина отклонения, уточнение причины).
2. Форма перехода: какие поля показать и куда их записать.
3. Бизнес-процесс: статусы, затем начальный статус, затем переходы с каналами, формой, условиями и действиями.
4. Сохранить и прочитать блок «Проверка конфигурации». Если ошибок нет, включить «Активен» и сохранить ещё раз.
5. Открыть заявку этого проекта в АРМ и нажать новую кнопку.

Готовый образец уже есть в демо: справочники «Причины отклонения» и «Уточнения причин отчисления», формы `decline` и `expel`, процесс «Код будущего: процесс с проверкой документов».

### Справочник значений

**Конструктор бизнес-процессов → Справочники значений → Добавить.**

| Поле | Что писать |
|---|---|
| Код | Латиница, уникален среди всех справочников. Например `decline_reasons`. По этому коду справочник попадает в экспорт JSON |
| Название | Как справочник называется в списке админки |

В таблице **Значения** каждая строка — пункт списка:

| Поле | Что писать |
|---|---|
| Порядок | Чем меньше число, тем выше пункт. Строки можно перетаскивать |
| Значение | То, что запишется в поле заявки. Например `no_places`. Менять значение у уже используемых пунктов не стоит: в старых заявках останется прежняя строка |
| Подпись | Текст, который видит сотрудник. Например «Отсутствие свободного места на площадке» |
| При значениях родителя | Нужно только для зависимого списка. Значения родительского списка через запятую, при которых этот пункт виден. Пусто — пункт доступен при любом выборе родителя. Пример: у пункта «Болезнь» стоит `legitimate`, у «Переезд» — `legitimate,not_legitimate` |
| Активно | Снятая галочка прячет пункт из новых форм. Уже сохранённые заявки не меняются |

Справочник, который выбран в поле формы, удалить нельзя.

### Форма перехода

**Конструктор бизнес-процессов → Формы переходов → Добавить.**

Форма не привязана к проекту: одну и ту же форму можно выбрать в переходах разных процессов. Правка формы сразу меняет все такие переходы.

| Поле | Что писать |
|---|---|
| Код | Латиница, уникален среди форм. Например `decline` |
| Заголовок формы | Заголовок внутри окна смены статуса |
| Описание для сотрудника | Текст под заголовком. Можно оставить пустым |

Дальше карточки **Поля формы**. Одна карточка — одно место, куда сохраняется ответ. Список «Поле модели» задан в коде, произвольное поле туда не добавить.

Поля прототипа:

| В списке админки | Куда пишется | Имя параметра по умолчанию |
|---|---|---|
| Заявка: Причина | `reason_choice` | `reason_choice` |
| Заявка: Уточнение причины | `reason_detail` | `reason_detail` |
| Заявка: Комментарий к причине | `reason_text` | `reason_text` |
| Заявка: Дата решения об отклонении | `bas_declined_date` | `bas_declined_date` |
| Заявка: Уровень | `difficulty_level` | `difficulty_level` |
| Заявка: Название итогового проекта | `final_project_name` | `final_project_name` |
| Заявка: Поток | `flow`, только активные незакрытые потоки курса этой заявки | `flow` |
| Заявка: Документ-основание (файл + ЭП) | файл и подпись становятся документом, ссылка пишется в `reason_document` | `reason_file` и второе поле `reason_file_ds` |
| Трансферт: … | одноимённое поле трансферта. Если трансферта ещё нет, он создаётся при сохранении перехода | имя поля, например `accept_date` |

Карточка поля:

| Поле | Что писать |
|---|---|
| Поле модели | Куда сохранить значение |
| Порядок | Порядок на форме. Карточки можно перетаскивать |
| Подпись | Текст над полем. Пусто — берётся подпись поля модели, например «Дата зачисления» |
| Имя параметра | Имя в запросе API и в условиях видимости. Пусто — имя из таблицы выше. Если задать своё, в «Показывать, если параметр» нужно писать уже его |
| Обязательное | Пустое обязательное поле не даст выполнить переход. Скрытое условием видимости поле обязательным не считается |
| Подсказка | Серый текст под полем |
| Справочник значений | Для полей-списков вроде причины. Без справочника причина была бы свободной строкой. Для даты, текста и файла справочник не выбирают |
| Вид списка | «Простой список» или «Список с автокомплитом». Имеет смысл только у списков: справочник, поток, поле модели с фиксированными вариантами |
| Зависит от списка | Другое поле **этой же** формы. Варианты сужаются по его значению. Новое поле появляется в этом списке только после сохранения формы |
| Показывать, если параметр / Равен | Поле рисуется, когда другое поле формы имеет указанное значение. Для флажка в «Равен» пишут `true` или `false`. Пример: комментарий к причине виден, только если параметр `reason_choice` равен `other` |

Зависимость списка работает по-разному:

- Оба поля берутся из справочников. Связь задаётся колонкой «При значениях родителя» у значений **дочернего** справочника. Если колонка пустая у всех пунктов, проверка формы предупредит, что список сужаться не будет.
- Оба поля выбирают объект модели, и у дочерней модели есть один внешний ключ на родительскую (поток ссылается на курс). Связь находится сама, «При значениях родителя» не нужно. В прототипе поток ограничен курсом заявки в коде, поэтому зависимость «поток от курса» на форме сама по себе новые курсы не откроет.
- Смешивать справочник и список из модели нельзя: при сохранении будет ошибка. Ошибка будет и если поле зависит само от себя или зависимости образуют круг.

Блок **Проверка формы** и сообщения сверху страницы появляются после сохранения. Ошибки и предупреждения форму не выключают: форму можно сохранить и с ними, но процесс, который её использует, с ошибкой не активируется.

Документ-основание на форме — одна карточка, в окне перехода из неё получается два файла: сам документ и подпись (ЭП). Подпись необязательна.

### Каналы

Канал — это откуда разрешено выполнить переход. Галочки стоят на карточке перехода, можно отметить несколько.

| Канал | Кто им пользуется |
|---|---|
| АРМ (кнопка) | Кнопка в списке и карточке заявки. Сотрудник видит только переходы с этой галочкой |
| API платформ | `GET /api/applications/<id>/transitions/` (канал по умолчанию — `api`) и `POST /api/applications/<id>/status/` |
| Система (задачи, интеграции) | Переходы, которые запускает код: задачи и интеграции. В прототипе отдельной задачи нет, канал уже можно отметить |
| Слушатель (ЛК) | Переходы из личного кабинета. В прототипе ЛК нет, отметка сохраняется для будущего переноса |

У нового перехода отмечен только АРМ. Если снять все галочки, переход нигде не появится: проверка процесса напишет предупреждение.

Кнопка в АРМ есть только у перехода из текущего статуса заявки с каналом АРМ. Запрос API с `status=accepted` ищет единственный переход канала API из текущего статуса в базовый статус «Зачислен». Если таких переходов два, вызов по базовому статусу неоднозначен: проверка покажет предупреждение, а API попросит передать `transition=<код перехода>`.

Код перехода уникален среди переходов **из одного статуса**. Из «На рассмотрении» и из «Одобрена» код `decline` можно использовать ещё раз: для API это разные переходы.

### Бизнес-процесс

**Конструктор бизнес-процессов → Бизнес-процессы проектов → Добавить.**

Сначала сохраните процесс с проектом и названием. Пока процесс не сохранён, статусы выбрать негде: списки «Начальный статус», «Из статуса» и «В статус» содержат только статусы этого процесса.

| Поле | Что писать |
|---|---|
| Проект | Проект без процесса. У проекта с процессом пункта в списке нет |
| Название | Как процесс называется в списке. Например «Код будущего: процесс с проверкой документов» |
| Начальный статус | Статус новой заявки. Выбирается после того, как статусы сохранены. Для уже существующей заявки без статуса проекта движок берёт первый статус процесса с тем же базовым статусом |
| Активен | Включайте в конце, когда в «Проверке конфигурации» нет ошибок. Если ошибки есть, галочка при сохранении снимется, сверху будет сообщение «Процесс не активирован» |

#### Статусы

Таблица **Статусы** на странице процесса:

| Поле | Что писать |
|---|---|
| Порядок | Порядок в списках и на графе |
| Код | Латиница, уникален внутри процесса. Например `docs_check`. Этот код уходит в API как `workflow_status` и в `to_status` схемы перехода |
| Название | То, что видит сотрудник: бейдж в АРМ и заголовок статуса в окне перехода |
| Базовый статус | Что видят интеграции. Проектных статусов может быть больше, чем базовых: «Проверка документов» в демо — отдельный статус с базовым «Одобрена» |
| Конечный | У статуса нет исходящих переходов. Если галочка стоит, а переходы есть, или галочки нет и переходов нет — это предупреждение, процесс включить можно |

Базовый статус менять у статуса, на котором уже висят заявки, нельзя без миграции данных: заявки держат ссылку на статус процесса.

Переход между **разными** базовыми статусами допустим только по этой матрице. Переход в тот же базовый статус разрешён всегда: так сделаны «Сменить поток» и любые другие петли.

| Из базового | Можно перейти в |
|---|---|
| На рассмотрении | Одобрена, Зачислен, Отклонена |
| Одобрена | Зачислен, Отклонена, Одобрена работодателем, Не допущен, Допущен, Перевод |
| Одобрена работодателем | Зачислен, Не допущен, Допущен |
| Допущен | Зачислен, Отклонена |
| Не допущен | Допущен |
| Зачислен | Отчислен, Окончил обучение, Перевод |

Для базового статуса «Отчислен» форма перехода обязана записывать причину: поле с привязкой «Заявка: Причина», обязательное и без условия видимости. На петле внутри одного базового статуса это требование не действует.

#### Переход

Каждый переход — карточка в блоке **Переходы**. Внутри неё ещё две таблицы: условия и действия.

| Поле | Что писать |
|---|---|
| Из статуса / В статус | Ребро матрицы. Оба статуса — этого процесса |
| Код | Латиница. Уникален среди переходов из того же статуса. Его передают в API как `transition` |
| Активен | Снятая галочка прячет переход, не удаляя его |
| Порядок | Порядок кнопок в АРМ слева направо |
| Текст кнопки | Надпись на кнопке. Например «Отклонить» |
| Стиль кнопки | Основная (синяя), Зелёная, Красная, Серая |
| Форма | Форма из предыдущего раздела. Пусто — окно только просит подтвердить переход |
| Каналы | См. раздел «Каналы» |
| Текст подтверждения | Жёлтая плашка в окне. Например «Слушатель будет отписан от курса.» |

После сохранения внизу страницы рисуется граф. Звёздочка на стрелке означает, что у перехода есть форма. Граф обновляется при сохранении.

#### Условия

Условие решает, можно ли нажать кнопку. Список условий задан в коде, в поле **Параметры** — JSON. Под полем перечислены параметры каждого условия. Пустой объект пишется как `{}`.

Если условие не выполнено, кнопка в АРМ остаётся на месте, но рисуется пунктиром, а причина видна по наведению. Выполнить переход нельзя. API отдаёт тот же переход с `"allowed": false` и текстом в `reasons`.

| Условие | Параметры | Когда пропускает |
|---|---|---|
| `project_expelling_allowed`, отчисления разрешены в проекте | `{}` | У проекта снята галочка «Отчисление запрещено» |
| `transfert_status_in`, статус трансферта входит в список | `{"statuses": ["activated", "conditionally_activated"]}` | Трансферт есть и его статус в списке. Допустимые значения: `booked`, `activated`, `conditionally_activated` |
| `flow_not_filled`, поток заявки не закрыт | `{}` | У заявки выбран поток и он не закрыт |
| `flow_filled`, поток заявки закрыт | `{}` | У заявки выбран закрытый поток |
| `not_finished_course`, слушатель не окончил обучение | `{}` | У заявки нет даты окончания и нет записи на курс с датой окончания |
| `setting_flag`, флаг в настройках | `{"name": "SHOW_EXPEL_AND_FINISH_BUTTONS"}` | Настройка Django равна ожидаемому значению. Второе значение по умолчанию — JSON `true`: `{"name": "SHOW_EXPEL_AND_FINISH_BUTTONS", "expected": true}` |
| `attr_in`, атрибут заявки входит в список | `{"path": "transfert.status", "values": ["activated"]}` | Значение по пути есть в списке. Путь идёт от заявки через точку: `flow`, `transfert.status` |
| `attr_not_in`, атрибут заявки не входит в список | `{"path": "difficulty_level", "values": ["advanced"]}` | Значения в списке нет |
| `attr_is_set`, атрибут заявки заполнен | `{"path": "flow"}` | По пути лежит непустое значение |

**Сообщение при отказе** заменяет текст по умолчанию на пунктирной кнопке. Пустое поле оставляет текст условия.

Неизвестное имя параметра и пропущенный обязательный параметр — ошибка конфигурации. Процесс с такой ошибкой не включится.

#### Действия

Действие выполняется после успешной смены статуса, сверху вниз по полю «Порядок». Параметры тоже JSON.

| Действие | Параметры | Что делает |
|---|---|---|
| `course_user_status_enroll`, записать слушателя на курс | `{}` | Создаёт или обновляет запись на курс, делает её активной |
| `course_user_status_expel`, отписать слушателя от курса | `{}` | Помечает запись на курс неактивной |
| `course_user_status_finish`, отметить окончание обучения | `{}` | Ставит дату окончания на записи и на заявке |
| `set_transfert_status`, сменить статус трансферта | `{"status": "activated"}` | Пишет статус трансферта. Если трансферта не было, создаёт его |
| `log_event`, записать событие в лог | `{"message": "заявка зачислена"}` | Строка в лог сервера, в журнал переходов не попадает |

Журнал переходов (**Конструктор бизнес-процессов → Журнал переходов**) только для чтения. Туда пишутся статусы, канал, кто выполнил переход и имена заполненных привязок. Сами введённые значения остаются в полях заявки и трансферта.

### Проверка и включение

Сохранение процесса прогоняет проверку. Ошибки показаны красным, предупреждения — жёлтым, и в списке процессов есть колонка «Проблемы».

Ошибки не дают оставить процесс активным:

- нет ни одного статуса или не выбран начальный статус;
- переход ссылается на статус другого процесса;
- базовая матрица запрещает такую смену базового статуса;
- в каналах указано неизвестное значение;
- неизвестное условие, действие или привязка, лишний или пропущенный параметр;
- из одного статуса два активных перехода с одним кодом;
- форма не заполняет обязательную причину при переходе в «Отчислен»;
- зависимость списка настроена неверно: родитель не список, список из модели зависит от справочника, между моделями нет одной связи, поле зависит само от себя или получился цикл.

Предупреждения процесс не выключают:

- не отмечен ни один канал;
- конечный статус имеет переходы или из неконечного статуса выйти нельзя;
- статус недостижим из начального;
- из одного статуса канал API или «Система» имеет несколько переходов в один и тот же базовый статус;
- условие видимости ссылается на параметр, которого нет на форме;
- автокомплит стоит у поля, которое не является списком;
- зависимый справочник без «При значениях родителя».

Та же проверка из консоли: `.venv/bin/python manage.py workflow_validate` или `workflow_validate <id проекта>`. Команда завершается с кодом 1, если есть ошибки.

### Что проверить в АРМ

Откройте http://127.0.0.1:8000/arm/, оставьте заявку нужного проекта и статуса.

- Кнопки идут в порядке поля «Порядок», цвет совпадает со стилем.
- Окно открывается по кнопке. Обязательные поля помечены звёздочкой. Условие видимости прячет поле сразу, без перезагрузки.
- Список с автокомплитом ищется по уже загруженным вариантам. Зависимый список сужается при смене родителя; значение, которое новому родителю не подходит, сбрасывается.
- Пустое обязательное поле оставляет окно открытым и показывает ошибку у поля. Успешное сохранение закрывает окно и обновляет статус в таблице.
- Пунктирная кнопка не открывает форму. Текст условия виден по наведению.

Тот же переход можно выполнить из Swagger: http://127.0.0.1:8000/api/docs, заголовок `X-Api-Key: demo-key`. В списке переходов будут только каналы, отмеченные у перехода. Для канала АРМ передайте `channel=arm`.

### Экспорт, импорт и клонирование

На списке процессов выделите одну строку.

- Действие **Экспортировать в JSON** скачивает процесс вместе с его формами и справочниками.
- Действие **Клонировать в другой проект** создаёт копию в проекте, у которого процесса ещё нет. Копия выключена. Формы и справочники с тем же кодом не копируются, а используются общие.
- Ссылка **Импорт из JSON** над таблицей делает то же из файла. Импортированный процесс тоже выключен: его нужно открыть, прочитать проверку и включить отдельно.

Команды делают то же самое: `workflow_export <id проекта> -o process.json` и `workflow_import process.json <id проекта>`.

## Демо-данные

- **Код будущего** — 7 статусов, из них «Проверка документов» — собственный статус проекта с базовым
  `approved`. Условия: статус трансферта, закрытый поток, флаг в settings. Отчисление с документом,
  который обязателен только при уважительной причине, и уточнением причины — список с автокомплитом,
  зависящий от выбранной причины. Поток при одобрении выбирается из списка с автокомплитом.
- **БАС** — короткий процесс без одобрения; отчисления запрещены настройкой проекта, кнопка видна как заблокированная.
- **Цифровые профессии** — без процесса: такие заявки остаются на старом коде.

## Перенос в cat-marketplace

- `workflow/` переносится как есть (под Django 2.0: `models.JSONField` → `jsonfield.JSONField`,
  `path` → `url`, убрать `@admin.display/@admin.action`).
- `core/workflow_hooks.py` → `rall/workflow_hooks.py`: привязки к `TicketApplication`/`Transfert`,
  условия и действия из `TicketApplication.change_status` и `Enrollment`.
- Переключение старого и нового кода — по наличию активного `Workflow` у проекта, в `Enrollment.change_application_status`,
  `finish_course`, `change_enrollment_status` и местах прямого вызова `change_status`.

Сознательно не сделано: сидинг процессов текущих проектов (PDC, BAS, KB), цепочка модулей КБ,
смена курса и «Уточнить информацию» как переходы-петли, права по ролям на уровне перехода.
